# Feature Specification: DB Storage with Nested Statistics Categories

**Feature Branch**: `react-router`
**Status**: Draft
**Input**: User description: "集計データをGoogle SpreadsheetでなくDBに保存し、集計・グラフの項目もネストできるようにしたいです"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - View Nested Statistics (Priority: P1)

ユーザーとして、vim-jpコミュニティのプロファイル統計を階層構造で閲覧したい。例えば「Vim / Neovim」カテゴリの下に「HEAD」「stable」などのサブカテゴリがあり、ドリルダウンして詳細を確認できる。

**Why this priority**: 階層構造での可視化がこの機能の核心価値。ユーザーがより詳細な分析を行えるようになる。

**Independent Test**: ダッシュボードにアクセスし、任意のカテゴリをクリックしてサブカテゴリの統計が表示されることを確認。

**Acceptance Scenarios**:

1. **Given** ダッシュボードが表示されている状態, **When** 「Vim / Neovim」カテゴリをクリック, **Then** 「HEAD」「stable」などのサブカテゴリ別の統計グラフが表示される
2. **Given** サブカテゴリの統計が表示されている状態, **When** 「戻る」または親カテゴリをクリック, **Then** 親カテゴリレベルの統計表示に戻る
3. **Given** ダッシュボードが表示されている状態, **When** ネストのないカテゴリ（例：OS）をクリック, **Then** そのカテゴリの詳細統計が表示される（サブカテゴリなし）

---

### User Story 2 - Data Persistence in Database (Priority: P2)

システム管理者として、集計データをデータベースに保存したい。Google Sheetsへの依存をなくし、データの一貫性と拡張性を確保する。

**Why this priority**: データ基盤の変更は階層構造表示の前提条件だが、既存のGoogle Sheets連携を維持しながら段階的に移行可能。

**Independent Test**: データ登録後、DBから直接データを取得してダッシュボードに表示できることを確認。

**Acceptance Scenarios**:

1. **Given** 新しい回答データがある状態, **When** データを保存, **Then** データベースに永続化され、再起動後も参照可能
2. **Given** DBにデータが保存されている状態, **When** ダッシュボードにアクセス, **Then** DBからデータを取得して統計を表示
3. **Given** Google Sheetsに既存データがある状態, **When** マイグレーションを実行, **Then** 全データがDBに移行され、整合性が保たれる

---

### User Story 3 - Submit Profile via Web Form (Priority: P3)

vim-jpコミュニティメンバーとして、Webフォームから自分のプロファイル情報を登録・更新したい。Google Formsを使わずに直接システムに入力できる。

**Why this priority**: 移行後のデータ収集手段として必須だが、初期は既存データのマイグレーションで統計表示が可能。

**Independent Test**: Webフォームにアクセスし、全カテゴリの回答を送信してDBに保存されることを確認。

**Acceptance Scenarios**:

1. **Given** フォームページが表示されている状態, **When** 全カテゴリの回答を入力して送信, **Then** 回答がDBに保存され、確認メッセージが表示される
2. **Given** 既に回答を送信済みの状態, **When** 同じユーザーが再度フォームにアクセス, **Then** 以前の回答が表示され、更新可能
3. **Given** フォームに入力中の状態, **When** 必須項目を空のまま送信, **Then** エラーメッセージが表示され、送信されない

---

### User Story 4 - Manage Category Hierarchy (Priority: P4)

システム管理者として、統計カテゴリの階層構造を管理したい。新しいサブカテゴリの追加や、既存カテゴリの階層変更ができる。

**Why this priority**: カテゴリ構造の動的管理は将来の拡張性に重要だが、初期リリースでは固定構造でも価値を提供できる。

**Independent Test**: 管理画面からカテゴリを追加し、ダッシュボードに反映されることを確認。

**Acceptance Scenarios**:

1. **Given** 管理画面が表示されている状態, **When** 「Vim / Neovim」に新しいサブカテゴリ「fork」を追加, **Then** ダッシュボードで「fork」が選択肢として表示される
2. **Given** 既存のカテゴリがある状態, **When** カテゴリを親カテゴリの下に移動, **Then** 階層構造が更新され、関連データの紐付けも維持される

---

### Edge Cases

- サブカテゴリにデータが存在しない場合、どのように表示するか？ → 「データなし」と表示し、グラフは空の状態で表示
- カテゴリ階層が3階層以上になった場合の表示 → 2階層までサポートし、それ以上は将来の拡張とする
- 既存データとカテゴリ構造の不整合が発生した場合 → 「未分類」カテゴリに自動振り分け
- ユーザーが既存選択肢と大文字小文字のみ異なる値を追加しようとした場合 → エラーメッセージを表示し、既存の選択肢を案内
- 管理者が選択肢を削除した場合、その選択肢を使用していた回答 → 回答データは保持（値は文字列として残る）

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムは統計データをデータベースに永続化できなければならない
- **FR-002**: システムはカテゴリの親子関係（2階層まで）を管理できなければならない
- **FR-003**: ユーザーは親カテゴリからサブカテゴリへドリルダウンして統計を閲覧できなければならない
- **FR-004**: システムはGoogle Sheetsからの既存データをDBへマイグレーションできなければならない
- **FR-005**: システムは以下の既存カテゴリを維持しなければならない: OS, Shell, 端末ソフトウェア, マルチターミナルプレクサ, ブラウザ, キーボード, ポインティングデバイス, IME, Vim/Neovim, プラグインマネージャー, LSP, 補完, Fuzzy Finder, taskrunner, colorscheme, statusline, snippet, ファイラー, ターミナル拡張
- **FR-006**: ユーザーはサブカテゴリレベルの統計をグラフで可視化できなければならない
- **FR-007**: システムは各回答エントリを適切なカテゴリ・サブカテゴリに紐付けて保存しなければならない
- **FR-008**: 管理者はカテゴリの追加・編集・階層変更ができなければならない
- **FR-009**: システムはWebフォームを提供し、ユーザーがプロファイル情報を入力できなければならない
- **FR-010**: ユーザーは以前の回答を確認・更新できなければならない
- **FR-011**: システムはフォーム送信時にバリデーションを実行しなければならない
- **FR-012**: システムはGitHub認証またはFirebase Authによるユーザー認証をサポートしなければならない
- **FR-013**: システムは認証済みユーザーのみがフォーム送信・更新を行えるようにしなければならない
- **FR-014**: 統計ダッシュボードは認証なしで誰でも閲覧できなければならない
- **FR-015**: 認証済みユーザーは既存カテゴリに新しいCategoryValue（選択肢）を追加できなければならない
- **FR-016**: ユーザーが追加した選択肢は即時反映され、全ユーザーが選択可能になる
- **FR-017**: 管理者は不適切な選択肢を削除できなければならない（事後モデレーション）
- **FR-018**: システムは同一カテゴリ内でcase-insensitiveに重複する選択肢の追加をブロックしなければならない

### Key Entities

- **User（ユーザー）**: 回答者を識別。属性: 外部認証ID（GitHub UIDまたはFirebase UID）、認証プロバイダー種別
- **Category（カテゴリ）**: 統計項目の分類。親子関係を持ち、最大2階層。属性: 名前、親カテゴリへの参照、表示順序
- **Response（回答）**: ユーザーからの1件の回答データ。ユーザーに紐付き、各カテゴリに対する選択値を持つ
- **CategoryValue（カテゴリ値）**: 各カテゴリで選択可能な値（例: OSカテゴリの「macOS」「Linux」「Windows」）。カテゴリに紐付く。属性: 追加者（User）、追加日時
- **StatisticsSummary（統計サマリー）**: カテゴリ・サブカテゴリごとの集計結果。キャッシュ目的で保持

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: ユーザーは任意のカテゴリを2クリック以内でサブカテゴリ統計まで到達できる
- **SC-002**: ダッシュボードの初回読み込みが3秒以内に完了する（既存と同等以上）
- **SC-003**: 既存のGoogle Sheetsデータ100%がDBへ正確にマイグレーションされる
- **SC-004**: 2階層のカテゴリ構造を持つ統計グラフが正しく表示される
- **SC-005**: カテゴリ追加後、1分以内にダッシュボードに反映される

## Clarifications

### Session 2026-01-27

- Q: データ規模の想定は？ → A: 回答データ〜1,000件（中規模）、カテゴリ値〜50件（小規模）
- Q: Google Sheets移行戦略は？ → A: 一度きりの移行、移行後は新規データはDBのみに保存
- Q: 移行後の新規データ入力方法は？ → A: 新規Webフォームを作成してユーザーが直接入力
- Q: ユーザー識別方法は？ → A: GitHub認証またはFirebase Auth（アカウントUID）
- Q: 統計閲覧のアクセス制御は？ → A: 公開（認証なしで誰でも閲覧可能）
- Q: ログインユーザーが追加できる項目は？ → A: CategoryValue（選択肢）のみ。カテゴリ自体の追加は管理者のみ
- Q: 選択肢追加の承認フローは？ → A: 即時反映 + 事後モデレーション（管理者が後で削除可能）
- Q: 重複する選択肢の扱いは？ → A: Case-insensitive（大文字小文字無視）で一致する場合はブロック

## Assumptions

- データベースの具体的な種類は実装フェーズで決定する
- 初期リリースではカテゴリ階層は2階層までとする
- 移行戦略: 一度きりのマイグレーション実行後、Google Sheetsは使用しない
- 日本語がプライマリ言語として使用される
- データ規模: 回答データ最大1,000件、カテゴリ値最大50件を想定
